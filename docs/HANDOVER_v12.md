# PondMerge v1 第十一轮：测量仪器轮报告（HANDOVER v12）

> 本轮不是功能轮，是**证据轮**。起因：为做 ESP32 实测而复核基准时，发现
> 前十轮所有**绝对**性能数字产自一个未量化的计时仪器，且在某些情形下仪器
> 就是被测对象的主要成本。本轮把仪器修好、把数字重测、并顺带发现并修掉
> 一个真实的库缺陷。
>
> 基线：`65aa133`（干净 worktree，= origin/main，CI 全绿）。
> 本轮提交见 git log（`bench/` 仪器 + 重测、`pm_port.h` 修复、文档）。

## 1. 本轮的实际发现（按重要性）

### 1.1 计时仪器在探针主机上是坏掉的（影响前十一轮的全部绝对值）

`std::chrono::steady_clock::now()` 在该主机上单次耗时 **~9,400 ns**，被测操作
只有 36–90 ns。原因是该 VMware 客机的 `RDTSC` 被拦截：时间戳**数值**正确
（200 ms 延时测出 200.024 ms），但**读取**要付一次 VM exit。数值准确恰恰是
缺陷长期隐形的原因。

每个变体在一个长区间内调用 200,000 次的实测：

| 变体 | 成本 |
|---|---|
| 空循环体 | 0.01 ns/次 |
| `g_sink += 1` | 0.44 ns/次 |
| 64 位 LCG 依赖链 | 1.01 ns/次（≈3 周期 ⇒ CPU 满速） |
| `__rdtsc()` | **10,244 ns/次** |
| `lfence; __rdtsc()` | 9,968 ns/次 |
| `__rdtscp()` | 9,936 ns/次 |
| `clock_gettime(CLOCK_MONOTONIC)` | 9,341 ns/次 |
| 裸 `syscall(clock_gettime)` | 19,530 ns/次（⇒ vDSO 生效但本身慢） |
| `clock()`（`CLOCK_PROCESS_CPUTIME_ID`） | **20,900 ns/次** |

空循环与 LCG 排除了"机器被限频/被抢占"的解释：成本在计数器指令内部。
**该主机上任何周期计数器指令都不可用**——被拦截的就是 `RDTSC` 本身，
换 `rdtscp`、加 `lfence`、直接读 TSC 都一样。

### 1.2 由此发现一个真实的库缺陷：host 端口层在给自己计时

`pm_port_ticks_us()` 的 host 分支实现为 `clock()`，即
`CLOCK_PROCESS_CPUTIME_ID`：

1. **成本**：glibc 上是系统调用，实测 **20.9 µs/次**。`compact()` 每次调用它
   **两次**填充 `compact_time_us`，于是库**唯一的性能统计量**为每次整理加进
   **~42 µs 的自测开销**——而它实际搬运的内存（184,296 B 拷贝）只要 **2.8 µs**。
   **仪器是被测对象的约 15 倍。**
2. **语义**：`clock()` 报的是进程 CPU 时间，不是墙钟时间，因此一个被抢占的
   维护窗口会被**低报**，也无法与任何墙钟预算比较。而"维护窗口统计"本质上是
   墙钟量。

**修复**：host 分支改用 `CLOCK_MONOTONIC`。ESP32 分支不动
（`esp_timer_get_time()` 本就是正确的墙钟源，且是寄存器读、非系统调用）。
**实测效果**：碎片基准中整理耗时从 80 µs 原始值降至 61 µs，纯来自去掉库自己
的时钟读取。

## 2. 仪器修复：`bench/bench_timer.h`

三条规则：

1. **按批计时，绝不逐次计时。** 一个区间装 N 次操作 ⇒ 仪器贡献从
   `2·call_cost` 降到 `2·call_cost/N`。N = 16,384 时约 1 ns/op 而非 18,800 ns/op。
   **与机器无关**，所以同一份源码在 host、普通 PC、设备上都给有效数字。
2. **每次运行自报仪器。** 后端、实测时钟成本、单区间偏置、"本机能否支持逐次
   计时"的裁定，全部打印。不能支持的运行直说。
3. **不产出逐次计时**，除非操作远长于时钟；那种情况也必须标注偏置。

另用**真实负载**标定"场景偏置"比紧凑循环更大（同一份 memmove 负载：
批量真值 2,780 ns、逐次 14,749 ns ⇒ 场景偏置 ≈11,969 ns；而紧凑循环探针给
7,521 ns）。因此 `RESULTS.md` 里的修正值**仍偏保守**。

`PM_ESP32` 分支用 `esp_cpu_get_cycle_count()`（mcycle，免费）。该分支**不使用
`__uint128_t`**：ESP32-S3 是 Xtensa，工具链没有 TImode，这一点是从**失败的
构建**里学到的，不是从文档。

## 3. 重测结论（`bench/RESULTS.md` 全文替换）

| 项 | 旧（仪器不可信） | 新（可靠仪器） |
|---|---|---|
| alloc 与 live 数 | 线性，斜率 1.42 ns/live | **pair 在 live 16→1024 上 x1.01（完全平坦）** |
| 方案 A 收益 @live=1024 | 799 → 37.6 ns（21×） | **844.2 → 38.4 ns（22×）**，同一基准源码对两个 core 修订 |
| `PM_MAX_OBJECTS=256` | 232 → 38.5 ns | **36.7 ns，同样平坦（x0.94）** |
| `validate` 指数 | ≈1.74 | **1.83**（二次确认） |
| `get_stats` | "便宜" | 指数 1.17、1.53–2.7 µs ⇒ **负结果保持** |
| `PM_SL_COUNT` 4/8/16 | 799/823/817 ns | **40.7/37.8/40.8 ns ⇒ 负结果确认**（旧版 SL8=48.0 是单次噪声，已记录） |
| 碎片 A/B | 50/50 vs 1/50；3/500 vs 0/500 | **逐项不变**（零 churn 拒绝、结构审计 OK） |
| 整理成本 | 25 µs | 0.061 ms 原始 / 0.053 ms 修正后 |

方案 A 的形状结论（线性 → 平坦）**不仅不变，而且被强化**：旧数字的误差预算是
未知的，新数字有已知边界。

新增的自我校验机制：`pair` 由 churn 直接测，`free`/`alloc` 由三段长区间差分得到
——两者是同一量的独立测量，不一致的行会被标 `REJECTED`。在 L=8192 上确实
发生了拒绝，而报告被拒绝的行本身是输出的一部分。
