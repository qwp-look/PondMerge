## 2. 方法：怎么让"一次整理"变成"512 次整理"

新基准 `bench/compaction_window.cpp`（host 与设备同一份源码）：

1. **复现 `fragmentation.cpp` 的状态**：同常数 fill（陡尺寸谱 + 每 16 个
   一个 pin）→ scatter（每 4 个槽位释放）→ **一次不计时**的整合（即被记录
   的那次整理事件：141 对象 / 138,856 B）→ 回填到满池。
2. **循环**：free K=14..20 个随机可搬迁对象 → 申请 10 KiB（**失败**，产品
   的触发路径）→ 只读建议 → **计时一次 `compact()`**（这就是整理窗口）→
   重试 → **按释放顺序回填同样的尺寸**。
3. 回填是能反复出事件的关键：不回填，第一次整合后池里剩一整块大尾部空闲，
   其后 probe 永远直接成功，整轮又只剩 1 次事件。K_MIN=14 的取法让整理后
   的尾部（≈K×1 KiB）装得下 probe 重试（host 12 KiB / 设备 10 KiB）。
   装不下的事件照样分开记录（`still_failed`）——host 上 24/512，S3 上 0。

**设备端参数**：S3 记 512 事件（样例状态 ~12 KiB），经典 ESP32 记 128
（.bss 余量只剩 ~12 KiB）——CMake 按 target 下发 `PM_BENCH_CW_EVENTS`。

## 3. 测量推翻了一处归因：scatter 把 pin 全释放了

碎片基准的文档一直说"维系碎片的是 pinned 屏障""洞被 pinned 邻居围住"。
**读代码即可证伪，且已实测**：scatter 按 `(i+1)%4==0` 释放，pinned 在
`(i+1)%16==0`——是其子集 ⇒ **全部 pin 随 scatter 一起被释放**，其后所有
测量都跑在 `has_pinned=0` 的池上。同序列探针实测：scatter 后
`has_pinned=0`，整合搬迁 189 对象 / 184,296 B——与 host 记录**逐字节一致**
⇒ 被记录的那次整理确实无 pin。处置：

- **负载不改**（改了就废掉全部已测记录与两颗芯片的可比性），只改注释与
  文档叙述；`fragmentation.cpp` 的 phase-2 注释、`bench/README.md` §4
  （**原文保留 + 证伪过程**）已更正。
- pin 的**真实**效应由开发版实测并记录：让 pin 在循环中存活（每 16 个对象
  一道屏障）时，`compact` 按屏障分段打包、屏障下方空闲全部搁浅成 ~1 KiB
  口袋 ⇒ **512 次整理后 probe 重试全部失败**（rescued=0/512）。这是
  COMPACTION_POLICY §7 定性预告的定量实例：**屏障密集时"整理以满足大块
  需求"可以在总空闲充足的情况下结构性失败**。正式版把 pin 留在 fill、
  测量前移除——因为被记录的 regime 就是无 pin 的。

1. **建议估算 vs 实际搬迁**：`analyze_compaction` 的
   `estimated_moved_objects/bytes` 与 `compact` 实际值在 **512/512 事件上
   偏差 0**（0 UNKNOWN）。R35 打包模拟的精确性此前只有故障注入测试，这是

2. **双时钟交叉校验**：库自带的 `compact_time_us`（esp_timer，µs）与

## 5. 复现性口径（比"逐字节相同"更诚实的一版）

- **状态层**：两轮的 moved-bytes 聚合、rescued/refusal 计数、估算校验
  **逐字节一致**（固定 seed ⇒ 状态确定）。
- **计时层**：p50/p75/p95/mean 两轮差 ≤0.008%，p90/p99 差 0.04–0.05%，
  min（单个事件）差 0.07%。机制：FreeRTOS tick 落进哪个区间带几百周期抖动
  （perfcount 的指令计数也随 tick 落点差几十条）。上一轮"三次运行逐字节
  相同"的结论**只属于当时的构建**；重建即把 §5.6 单点从 7,583 移到
  7,589.9 µs（本轮构建两轮逐字节相同；中间一次未提交构建给 7,587.3）——
  **代码布局敏感 ~0.1%**。引用设备数字时必须说明是哪次构建的两轮。

## 7. 现在已知的边界（不要越线声称）

- **百分位只属于一个 regime、一颗芯片**：S3、满池、无 pin、14–20 个分散洞。
  经典 ESP32 的百分位**未取**（板子本轮离线；其固件因 .bss 只记 128 事件）。
  pinned-barrier regime 只有开发版观测（512 rescued=0），**不是分布记录**。
- **无老化/长跑**：512 次事件只覆盖 ~4.5 s 的整理时间、~30 s 的固件。
- 计时层两轮差异见 §5；**"逐字节相同"不再作为设备数字的默认声明**，
  必须按构建 + 两轮的实差引用。
- host 侧一切照旧：该 VM 上 `RDTSC` 陷阱**已消失**（`bench_timer` 自报
  时钟成本 19–26 ns，与文档记录的 ~9,400 ns 不同）——host 逐次/逐事件
  数字依旧不可引用（规则没变，机制换了），但 §0 里"每次读取 2.7 ms"的
  旧行文对这台机器的当前状态已不成立。

## 8. 复用要点

- **让"只发生一次"的事件可重复 = 找到并重建它的前置状态**。整理窗口的
  前置状态是"满池 + 分散洞"，而第一次整理会把这个状态永久消掉——所以
  每个事件后要**按释放顺序回填同样的尺寸**。回填不足（池不满）会让大块
  尾部空闲吃掉所有后续 probe；回填过度（超容量）就是越界。
- **"可搬迁"子集选取要查与释放模式的包含关系**：`每16个pin` ⊂ `每4个
  scatter`，屏障就在眼皮底下被放掉了。凡是"每 N 个"式的两个节奏共存，
  先算最小公倍数关系。
- **zsh 的 glob 全有或全无**：一条命令里一个通配失败 = 整条不执行且只报
  第一个失配项。判设备在线别用多通配 `ls`。
- **抓实机记录前先 `git status`**：IDF App version 带 `-dirty` 的抓取
  无法与提交对账，作废重抓（烧一次 ~40 s，别省）。
- **基线返回码语义**：`idf_heap_baseline` 以 1 返回 CONFOUNDED，
  `=== benchmarks done (rc=1)` 在 S3 上是**预期值**，不是失败。
