# PondMerge v1 第十二轮：第二颗芯片与指令数报告（HANDOVER v13）

> 起因有二。其一，上一轮（v12，仪器轮）修好了计时仪器并把设备基准固件构建
> 到位，但**板子离线**，实测未执行；本轮板子回来了。其二，用户提供了第二颗
> 芯片（经典 ESP32），使"锁语义只能由双核设备测试证明"这条最载重的声明
> 第一次有了**两颗不同架构**的支撑。
>
> 基线：`a5e6...`（v12 结束、CI 全绿）。本轮提交：
> `fcf999e`（第二颗芯片 + 目标分叉）→ `b4a7b6c`（基准搬到第二片）→
> `5c158b7`（串口 open 重试 + 复现性）→ 本轮收尾（perf 计数器 + 指令数）。
>
> **本轮最重要的结果**：v12 留下的一个假说被**直接测量推翻**——设备侧那个
> ~20×/周期的差距**不是 cache 未命中**（两个未命中计数器读数**恰好为 0**），
> 而是**指令数**：同一对 `free`+`alloc`，目标执行 **1,528 条指令**，x86-64
> 执行 **757 条**（callgrind 实测），其余是 CPI。

## 0. 环境与板子状态（接手者必读）

| | ESP32-S3 (n16r8) | 经典 ESP32 (D0WDQ6 v1.1) |
|---|---|---|
| 串口 | `/dev/ttyACM0`（USB-Serial-JTAG） | `/dev/ttyUSB0`（**CH340** 桥接，需 `dialout` 组） |
| Flash | 16 MB | 4 MB |
| 静态 DRAM | 512 KiB 档 | **约 200 KiB**（`dram0_0_seg` = 204,800 B） |
| IDF 默认主频 | —（基准显式 240 MHz） | **160 MHz**（基准同样显式 240 MHz） |
| 当前固件 | 未插（被换下） | **基准固件**（`bench/esp32/`） |

**两块板共用同一个 USB 口**，换板时内核会出现
`usb 1-2.1: USB disconnect` 紧跟新设备——这是换板，不是故障。

## 1. 锁语义的证据从一颗芯片变成两颗

`esp32/` 验收固件按 `CONFIG_IDF_TARGET` 分叉：

| 目标 | 编译组 | zone |
|---|---|---|
| esp32s3 | suite + concurrency + model | 256 KiB |
| esp32 | concurrency + model | 64 KiB |

**为什么套件不能在经典 ESP32 上跑**：`tests/suite.cpp` 的 zone 尺寸写在自己的
断言里（测试 [10] `CHECK(made == 16)` = 16 池 × 4 段填满 64 段 zone；测试 [2]
要 32 段池）。该芯片静态 DRAM 总量约 200 KiB，链接实测
`dram0_0_seg overflowed by 126,744 bytes`。⇒ **跳过必须大声声明**：
`=== suite SKIPPED (not run, not passed) ===`，绝不写成"通过"。

结果（两组各复位重跑两次，**核验计数一致**）：

```
ESP32-S3      suite 1,120,457 / concurrency 28 / model 466,859  checks, 0 failures
经典 ESP32    suite SKIPPED / concurrency 28 / model 466,859    checks, 0 failures
```

**为什么值得**：`PM_LOCK` 在 host 是空操作，SMP 证据只能来自双核设备测试，
而此前它只在**一颗**芯片（LX7）上成立过。经典 ESP32 是 **LX6**，`portMUX`
实现与 cache 都不同。经典板上并发竞争还**更激烈**：200 轮里 30 次整理因存在
活跃借用被拒（S3 那次有一个借用者的暂停命中数为 0）。

## 2. 基准搬到第二片（第二个绝对数据点）

`bench/esp32/main/CMakeLists.txt` 同样按目标分叉；**唯一被迫改的参数是
region**（112 KiB vs S3 的 192 KiB，DRAM 逼的；128 KiB 实测溢出 4,208 B）。
其余参数——live 数、churn 区间、probe 大小、pin/scatter 节奏——**两片逐项相同**，
否则第二个数据点就不是同一个实验。两片同 **240 MHz**（经典板上显式设，
IDF 默认 160）。

| 项 | S3 (LX7) | 经典 (LX6) |
|---|---|---|
| `alloc`/`free` 平坦性 | x0.99 | **x0.99** |
| churn 分解：两估计之差 | 0.4% | 0.6% |
| `validate`/`get_stats` 指数 | 1.70 / 0.75 | **1.70 / 0.75** |
| 碎片 A → B | 50/50 → 1/50 | **50/50 → 1/50** |
| 独立 TLSF 基线 | 50/50 | 50/50 |
| 整理代价 | 7.583 ms / 138.9 KB | **3.5388 ms / 79.0 KB（22.3 MB/s）** |

**TLSF 基线的持续 churn 计数这次可引用**（经典板 0 次同尺寸拒绝，S3 那次 1 次
被标 `CONFOUNDED`）：**未整理的 TLSF 掉 21/200（10%）的大块需求，PondMerge 开
整理掉 0**。核心主张从"成立"升级为"有量级、跨架构、对第三方"。

## 3. 决定性实验：那 ~20×/周期 **不是 cache**（本轮最重要的修正）

v12 与更早的文档把设备/host 的每周期差距猜成"内存与代码访问"。这是**猜测**，
而 S3 的 Xtensa 性能计数器让它**可测**：
`bench/esp32/main/perfcount.cpp` 跑与 `churn_overhead` 相同的三个工作负载，
两个计数器与 `mcycle` **取自同一次试验**（占比是精确值，不是两次运行的商）。

| 工作负载 | icache 未命中代价 | dcache 未命中代价 | 指令数/op | 周期/op | CPI |
|---|---|---|---|---|---|
| 平凡循环 | **0** | **0** | 5.01 | 5.02 | 1.00 |
| 地址生成 | **0** | **0** | 12.01 | 12.02 | 1.00 |
| **free+alloc** | **0** | **0** | **1,528.4** | **2,160.6** | **1.41** |

**两个未命中计数器读数恰好为 0，三个工作负载全是。** "内存与代码访问"的旧解释
**被直接证伪**（`RESULTS.md` §5.3 特意保留错误原文以示教训）。

真实去向（同一批计数器）：

| | 每 op | 占比 |
|---|---|---|
| 指令数 | 1,528.4 | （CPI 1.41） |
| **hold/bubble 周期** | **524.0** | **24.3%** |
| I 相关停顿 | 66.7 | 3.1% |
| D 相关停顿 | 0.8 | 0.04% |
| cache 未命中代价 | 0 | 0% |

⇒ 成本是**指令数 + 流水线依赖气泡**，不是内存停顿。

**host 侧补上了指令数**：`bench/host_insn.cpp` + callgrind，**两个运行长度做差分**
抵消进程启动（与库自己的 `free`/`alloc` 归因同一技巧）——**x86-64 上同一对操作
757 条指令**。⇒ **目标执行 2.0× 的指令**（指令集与 32 位 ABI 的部分，两侧都实测）。

**不对称处要如实说**：host 的 CPI **不可引用**——VM 里 `perf` 被
`perf_event_paranoid` 禁掉，而拿实测时间除以标称频率正是 §0 要防的错误
（虚拟机里的真实频率不是 `lscpu` 印的）。所以 §5.7 只报设备侧 CPI 1.41。
推论：这 20× 是"指令数 × 2 + CPI 更差"，**是核与代码的性质，不是字节放在哪**；
它也回溯解释了 §6.3（简单循环更快、长依赖链更慢的第二颗芯片，正是指令数解释
所预测、内存延迟解释所不预测的）。

## 4. 元数据公式的 ABI 修正（文档缺陷）

`README.md` 曾把 `metadata_bytes = 72 + 476×POOLS + 98×OBJ` 写成"Host/ESP32 同"。
**错**：`ObjectDesc` 含指针，Xtensa 上是 **52 B**（x86-64 是 64 B），每对象约
**82 B** 而非 98 B。设备实测 256 对象/16 池 = **28,672 B**（闭式给 32,776 B）。
两份 README 都改为"**算预算直接读运行时的 `metadata_bytes`**"。发现途径：
`bench_main.cpp` 每次运行打印目标 ABI 的 `sizeof`。

## 5. 串口的两类故障（都实测过、都已处置）

| 故障 | 现象 | 处置 |
|---|---|---|
| **CH340 桥接挂死** | `/dev/ttyUSB0` 仍在、`lsusb` 仍列出芯片，但 open 报 EIO，内核持续刷 `ch341-uart: failed to send control message: -110` | **重插**或 root 重绑定；软件无法恢复。**ESP32 本身没事** |
| **open 偶发 EIO** | 同一命令里第 1 次 open 抛 `OSError [Errno 5]`，第 2 次正常并完整抓完 | `tests/serial_cap.py` 现已**重试 20 次**（注释带证据） |

诊断教训：**先分步手工验证（open→read→dtr/rts→复位脉冲→read），再动工具**。
手工全成功 ⇒ 端口与芯片都好，`-110` 只是内核里可重试的非致命错误，问题在工具
没有重试。没有重试时，一次偶发失败会终止一次本可成功的抓取，而 traceback 指向
串口、不指向真因。

## 6. 过程中修掉的缺陷（全部实测驱动）

1. **`pondmerge_run_model()` 把 zone 参数钳到硬编码 256 KiB**，而它借用的
   buffer 尺寸它不知道——换小 buffer 芯片后会**允许越界**。改为按数组自身尺寸
   钳位（引入共享宏 `PM_TEST_ZONE_BYTES`）。
2. **README 仍声称"设备端验收未执行（板子离线）"**，而它两轮前就跑过。已修，且
   两条实机记录**分别标注 App version**（它们不在同一提交上）。
3. **`bench/esp32/sdkconfig` 被跟踪**却每次构建都重新生成 ⇒ 取消跟踪，改
   `sdkconfig.defaults`（含**关看门狗**：churn 区间是几十毫秒纯 CPU 循环，正是
   任务看门狗要抓的，其串口打印会给区间注入数百微秒抖动——首版触发 3 次）。
4. **`bench/esp32` 原是 Debug(-Og)@160 MHz** ⇒ 改 `-O2`@240 MHz。**基准不能用
   调试构建测**。
5. `PM_BENCH_SEGMENTS` 从手写 48 改为**从 region 推导**（池段数与 region 不一致
   不再可表达）。S3 重建后 **ELF/bin/.bss/.data 逐字节相同** ⇒ 重构构造上中性。

## 7. 现在已知的边界（不要越线声称）

- **验收套件只能在 256 KiB-zone 档位运行**（zone 尺寸在断言里）。小内存目标跑
  concurrency + model 并声明跳过。
- **`bench/esp32/` 经典 ESP32 的基准记录是三次运行且逐字节相同**（连中位数列都
  相同；每次独立上电）。⇒ 设备侧数字**无离散度项**；**"±4%"那是主机的性质**
  （VM/被拦截的 RDTSC）。**相同 ≠ 正确**：系统性错误同样精确复现。
- **host 的 CPI 不可引用**（perf 被禁、标称频率不可信）⇒ 20× 分解中"指令数"两侧
  实测、"CPI"仅设备侧实测。
- **整理窗口百分位仍未取**（每次运行只触发 1 次整理）。
- **无 PSRAM 轴**（经典板是 WROOM 档，无 PSRAM）。
- **无老化/长跑**：基准 ~28 s，验收为"两次复位重跑"级。

## 8. 复用要点

- **换板子先看内核日志**：同一 USB 口 `disconnect` + 新设备 = 换板。
- **经典 ESP32 没有 USB-Serial-JTAG 外设** ⇒ 控制台必然 UART0 经 CH340。
- **加 IDF 目标**：`sdkconfig.defaults.<target>` 不会自动生效；defaults 列表里
  靠后的文件**改不动 `CONFIG_IDF_TARGET`**（target 用首个匹配猜测）⇒ 必须
  `idf.py set-target`。把 A 目标覆盖混进 B 目标构建会得到"真实链接失败 + 无意义
  数字"。
- **别指望缩小验收套件**：它的 zone 尺寸在断言里。要么给够内存，要么少跑一组并
  **大声声明**。
- **有性能计数器就直接数**，别从比值推断：Xtensa perfmon 的
  `ICACHE/DCACHE_MISSES` 直接给"以周期计的未命中代价"，`INSN` 给 CPI。
- **复现性用 `diff` 验证**（剥掉启动横幅），并区分"运行次数"与"复现次数"、写明
  离散度属于哪一侧；**相同 ≠ 正确**。
- **Windows 上别用 Python 文本模式改写远程脚本**（`\n`→`\r\n` ⇒ bash 报
  `syntax error ... $'\r'`）；用 `Write` 直接写，或 `sed -i 's/\r$//'` 后复核。
- **`bash -s` 再加文件参数会忽略该文件**（读空 stdin ⇒ 静默 rc=0、零输出）。
- **Xtensa 上 `uint32_t` 是 `unsigned long`** ⇒ `printf("%u")` 是 `-Wformat`
  错误；这也是这些基准里到处 `(unsigned)` 转型的原因。
