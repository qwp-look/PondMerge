# bench/ 实测结果

> **平台**：Host x86-64（Ubuntu 26.04，g++ 15.2.0），`-O2 -DNDEBUG -DPM_DEBUG=0`
> **代码基线**：`a35a7fb`
> **编译期配置**：除注明外为 `PM_MAX_OBJECTS=1024 / PM_MAX_POOLS=16 / PM_SL_COUNT=4 / PM_FL_MAX=24`
> **Auto Zone**：256 KiB，segment 4 KiB
>
> ⚠️ 以下为 **Host 数据**。复杂度**形状**（线性 / 二次）是架构无关的，
> **绝对值不可外推到 ESP32**（x86 ~3 GHz 下 1.4 ns/步，ESP32-S3 @240 MHz 量级可能高一个
> 数量级）。设备端数字见每次实测记录。

## 1. `alloc` 的成本几乎全在地址序插入（`order_insert_sorted`）

### 填充法：alloc 耗时随 live 数增长（`PM_SL_COUNT=4`）

| live 区间 | 平均 alloc |
|---|---|
| 0–63 | 140 ns |
| 128–191 | 300 ns |
| 256–319 | 469 ns |
| 512–575 | 821 ns |
| 768–831 | 1371 ns |
| 960–1023 | **1453 ns** |

填充段是地址升序分配（取最低地址的适配块），插入点**恒定落在链表末尾**，
所以这条曲线测的是 **O(n) 最坏情形**。斜率 ≈ **1.42 ns / live 对象**。

### 稳态（live=1024，随机插入位置）

```
free  avg:   45.4 ns
alloc avg:  798.9 ns
pair  avg:  844.3 ns
```

**关键交叉验证**：最坏 1453 ns（走满 n 步）÷ 2 = 727 ns ≈ 随机 799 ns（期望 n/2 步）。
⇒ **alloc 的成本几乎 100% 就是走链**；`bins_find`、块头写入、统计更新都在噪声级。

### live 数标度（`PM_MAX_OBJECTS=256`，MCU 典型配置）

| 项 | live=256 | live=1024 |
|---|---|---|
| 稳态 alloc | **232 ns** | 799 ns |
| 稳态 free | 39.6 ns | 45.4 ns |
| `metadata_bytes` | 31,816 B | 108,040 B |

4× 对象数 → 3.44× alloc 耗时 ⇒ **线性确认**。

### 负结果：调大 `PM_SL_COUNT` 无效

| 配置 | 填充均值 | 稳态 alloc | 稳态 free | 元数据 |
|---|---|---|---|---|
| SL = 4 | 868 ns | **799 ns** | 45.4 ns | 107,072 B |
| SL = 8 | 779 ns | 823 ns | 48.1 ns | 112,192 B |
| SL = 16 | 1113 ns | 817 ns | 47.0 ns | 122,432 B |

**假设被推翻**：瓶颈不在 bin 内 first-fit 走链，而在地址序插入。调大 SL
无改善且元数据线性增长 ⇒ **默认值 4 合理，不应再讨论**。

### Debug vs Release

| 构建 | 稳态 alloc | 稳态 free |
|---|---|---|
| Release | 799 ns | 45.4 ns |
| Debug（`PM_DEBUG=1`） | 882 ns | 42.6 ns |

断言开销约 **+10%** ⇒ 热路径上增加少量运行时检查是可承受的。

**结论**：`alloc` 声称的 O(bin 链长 + live_objects) 中，**`live_objects` 项 ≈ 全部成本**。
这是唯一值得动的复杂度热点（见 `PondMerge_复杂度优化评估.md`）。

## 2. `validate` 确为二次，`get_stats` 不是问题

| live | 已释放（≈空闲块） | `validate` | `get_stats` |
|---|---|---|---|
| 64 | 32 | 14.1 µs | 89.0 ns |
| 128 | 64 | 37.3 µs | 115.5 ns |
| 256 | 128 | 119.1 µs | 189.2 ns |
| 512 | 256 | **860.6 µs** | 407.4 ns |
| 1024 | 512 | **2574.5 µs** | 937.8 ns |

- `validate`：块数 192 → 1536（8×），耗时 14.1 → 2574.5 µs（**183×**），指数 ≈ 1.88
  ⇒ **二次确认**。诊断路径，不是热路径。
- `get_stats`：1536 块时 938 ns（≈0.6 ns/块），严格线性且绝对值极小
  ⇒ **负结果：不值得优化**（即使 advice 以 10 Hz 轮询，CPU 占用也是 0.01% 量级）。

## 3. 碎片治理到底有没有用（`fragmentation.cpp`）

负载：填充至耗尽（255 对象，其中 15 个 pinned 栅栏）→ 释放每第 4 个对象制造
被存活/pinned 邻居围住的孤立空洞 → Phase 1 = 连续 50 次大块申请（无 churn）
；Phase 2 = 100,000 步 churn 中每 200 步一次大块申请。申请量均为 **12,288 B**。

| 变体 | Phase 1 失败 | Phase 2 失败 |
|---|---|---|
| **A：关闭整理** | **50 / 50（100%）** | 3 / 500（0.6%） |
| **B：probe 失败时整理** | **1 / 50（2%）** | 0 / 500（0%） |

整理的代价：**1 次 compact，0.025 ms（25 µs），搬迁 189 对象 / 184,296 字节**。
两次运行 `churn_refusals` 均为 **0**（未被混淆），`validate` 均为 **OK**。

**读法（含必要的限定）**：

- Phase 1 是**状态**测量，不是速率：它说明"被 pinned 栅栏围住、且空洞尺寸与需求
  不匹配"的池，在不整理时**完全无法满足**一次大块申请（50/50）。变体 B 中被一次
  compact 救回后其余 49 次全部成功 —— 这不是取巧，**这正是被检验的结论本身**。
- Phase 2 是**速率**测量，而它的数字偏温和（A 仅 0.6% 失败）。**原因是真实的**：
  首次适配会让对象逐渐向低地址靠拢、空闲区向高地址聚集，未经整理的池也会随时间
  **自行缓解**（A 的最终最大空闲块达 76,288 B）。所以"持续 churn 下不整理也基本能用"
  在**这个负载**下是成立的。
- 因此本实验支持的结论是：**PondMerge 的显式整理把"碎片化状态下完全不可用"
  变成"可用"，代价是微秒级的一次搬迁；它并不意味着没有整理就一定会长期失败。**
  `PINNED_EVERY` / `PROBE_BYTES` / `SCATTER_MOD` 都可 `-D` 覆盖，换负载请重新测量。

## 4. 引用这些数字时必须同时给出

- 平台（Host x86-64 / ESP32-S3）与构建档（Debug / Release / `-O2`）
- 编译期配置（`PM_MAX_OBJECTS`、`PM_SL_COUNT`、`PM_FL_MAX`）
- 基准参数（population / probe / steps / pinned_every / scatter_mod）
- 若是 `fragmentation.cpp`：`churn_refusals` 是否为 0

**负结果必须保留。** 实测排除掉的候选（`PM_SL_COUNT` 调大、`get_stats` 优化）比"没测"
有价值得多：它们防止了后续为无收益的改动去破坏已被验证的代码。
